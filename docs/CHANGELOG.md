# Cantil — Completed Work Log

Implementation history for completed roadmap items, moved out of `AGENTS.md` to keep per-task context small. Authoritative detail lives in the code, `docs/ca/NN-*.md`, and git history; this file is the human-readable index of what shipped and when.

## Phase 3 — Bazel becomes the default build (2026-07-26)

Full detail in [docs/roadmap/bazel-migration.md](roadmap/bazel-migration.md).

- **The OpenSSL gate is a Bazel test.** `cantil_ztest(openssl_gate = True)` on the four DER-minting suites adds `<suite>_openssl_gate`, running the *same* `scripts/openssl_gate.sh` the CMake path uses. `bazel test //firmware/tests/...` is no longer weaker than `scripts/test.sh` — the item that had blocked retiring CMake. Stricter than the CMake runner in one place: a gated suite emitting no artifacts fails, where an empty directory used to pass trivially.
- **zephyr-bazel is hermetic.** `local_path_override` at a hand-patched `~/zephyr/zephyr-bazel` → `git_override` + `patches` in MODULE.bazel. `scripts/setup_bazel.sh` deleted; there is no setup step for a Bazel build. Verified by moving the local checkout away, deleting the fetched repo and rebuilding — firmware links, 21/21 sim tests pass, and every action cache-hits afterwards (so the fetched-and-patched tree is byte-identical to the checkout it replaced).
- **libcantil ported** — library, `cantil` CLI (own package so the binary keeps its name) and the X.509 conformance test. Needs `--config=host`: it links the system libsodium/libcrypto by design, and Pigweed's `host_clang` ships a sysroot without those headers. Backend selection is a `string_flag` (`--//libcantil:x509_backend=wolfssl`). `CANTIL_CLI_STATIC` not ported — AppImage packaging still uses CMake.
- **factory + wipe_diag ported.** Both bench images build; sizes within ~2 % of CMake (both smaller). The factory image still carries `lfs_format` / `fs_mkfs` / `littlefs_mkfs` under Bazel exactly as under CMake, and production still carries none.
- **UF2 output added** (ninth zephyr-bazel gap, and the real blocker for retiring west): zephyr-bazel had no `CONFIG_BUILD_OUTPUT_UF2` equivalent, so a Bazel-built image could not be flashed at all. `zephyr_app` gained `uf2_family`; the conversion must sit inside the app's platform transition, since the objcopy that produces the intermediate hex only resolves there. Start address `0x1000`, matching CMake.
- **`scripts/build.sh` and `scripts/test.sh` now drive Bazel**, with `--cmake` for the legacy west path. That path survives for two things only: the reference build for A/B size checks, and non-XIAO boards — which select it automatically and say so. (The mcuboot tier was the third and was dropped the same day; see Deprecations.) `scripts/setup_zephyr.sh`, the west workspace and the NCS host-tool bundle are needed only for `--cmake`.
- **The build asserts its own security invariants.** `//firmware:cantil_invariants` and `//firmware/factory:cantil_factory_invariants` are genrules over the linked ELF: production must carry `__wrap_lfs_format` and none of `lfs_format` / `__real_lfs_format` / `fs_mkfs` / `littlefs_mkfs`; the factory image must carry all three formatter symbols; neither may contain an `mbedtls_*` symbol. Previously verified by hand with `nm` and written up in prose. A genrule rather than a test because the ELF lives inside the app's platform transition, where a host test cannot run — and because a build action cannot be skipped. `scripts/build.sh` builds them alongside the UF2. This is parity: `firmware/CMakeLists.txt` already asserted the no-format invariant, so the *default* build system had been the weaker one. The checker ([scripts/check_elf_symbols.py](../scripts/check_elf_symbols.py)) parses the symtab itself rather than shelling out to `nm`, which would mean pulling `arm-zephyr-eabi-nm` into the exec configuration.
- **Pin drift between `west.yml` and `MODULE.bazel` is a test now**, not a comment. Each file carries a `# PIN: <project> <version> <sha>` marker; `//scripts:pin_agreement_test` checks that the two markers agree, that each marker's commit is what MODULE.bazel really pins, and that each marker's version is what west.yml really names — so any one-sided edit fails. That the tag really peels to the commit still needs a network and stays a human check when the pin moves. Runs under `--config=host` (no Zephyr in it); `scripts/test.sh` runs it after the suites on a full run.

## Deprecations

- **MCUboot bootloader tier — deprecated *and removed* 2026-07-26.** Superseded by wolfBoot ([docs/roadmap/wolfboot-migration.md](roadmap/wolfboot-migration.md)): one crypto library instead of two now that the firmware is wolfCrypt-only, GPLv3-compatible, standalone nRF52840 with Ed25519, and no sysbuild/`merged.hex` step. It was frozen for one day and then **deleted** — a tier nobody may build, validate or port is not a safety net, only a second flash layout, a second signing pipeline and a `--sysbuild` code path every future change has to keep compiling. Gone: `firmware/sysbuild/`, `boards/xiao_ble_nrf52840_sense_mcuboot.*`, `firmware/src/fw_update/`, `protocol.c`'s BEGIN/CHUNK/COMMIT handler, `CANTIL_BOOTLOADER_MCUBOOT` + six `CANTIL_FW_*` symbols, the `mcuboot` project in `west.yml`, `--bootloader` / `--signing-key` / the `merged.hex` step in `build.sh`, the imgtool signing block in `firmware/CMakeLists.txt`, and `imgtool` from `requirements.txt`. Kept because wolfBoot needs them: opcode 0x33 and the `ERR_FW_UPDATE_*` codes (0x33 still reboots into the UF2 bootloader on `uf2_only`, which is all it ever did there), the entire client side (`cantil fw-update` → `CANTIL_ERR_NOT_SUPPORTED` until wolfBoot), `storage_fw_pending_*`, and the FW LED patterns. Non-XIAO board `.conf`s keep `CONFIG_BOOTLOADER_MCUBOOT=y` — that is a statement about *those boards'* stock bootloaders, and the symbol is Zephyr's own (`modules/Kconfig.mcuboot`), needing no module in the manifest. Still deferred to the wolfBoot tier: `LED_PATTERN_FW_VALIDATING` / `LED_PATTERN_FW_WIPING`, the `firmware/tests/fw_update/` suite, the hardware end-to-end update test. `uf2_only` is the only tier meanwhile — an accepted, temporary regression in the security story. Also removed the last dangling reference to the long-dropped `UF2_MCUBOOT` tier (a `CANTIL_FW_SLOT_SIZE` default in `firmware/Kconfig`).

**`CMD_PROVISION_CA` (0x34) landed (2026-07-23):** `ca_init()` no longer provisions in any configuration — an empty slot 0 is a normal, non-error state that it logs and leaves alone, because it is also exactly what a provisioned device looks like when its partition has been misdeclared. Minting the root CA is now opcode 0x34: unlocked device, authenticated Noise session, tap-confirmed, refused in identity-recovery mode. `CANTIL_NO_AUTO_PROVISION` was **removed** rather than defaulted to `y` — a guard against unrecoverable key loss that a board `.conf` can switch off is not a guard. Moving `ca_provision()` from a boot path to the wire pulled in two things the design hadn't specified: it must refuse to overwrite (returns `-EEXIST`, checked independently of the dispatcher; `test_07` asserts the key blob is byte-identical afterwards, not merely that the call failed), and clients need to *see* provisioning state, so `DEVICE_STATUS` grew a `ca_provisioned` byte at offset 26 (wire 26→27 B, client parses it only when the response is long enough) and master-CA opcodes 0x01–0x06 return the new `ERR_NOT_PROVISIONED` (15) instead of a generic storage error. `ERR_ALREADY_PROVISIONED` is 16. `cantil provision-ca` does both device steps, so the user-facing workflow is unchanged. 201,212 B (+292). Suites: 16 / 186 tests (ca_bootstrap 6→8). **Caveat:** this moves the decision to a human, it does not inform one — a human looking at "NOT PROVISIONED" knows no more than `ca_init()` did. Marker enforcement is what closes that (landed the same day, below).

**Marker enforcement / degraded mode landed (2026-07-23):** the volume marker now restrains something — from 07-22 to 07-23 an invalid volume was detected, logged, and then used exactly as if it had verified. Two gates in `storage.h`, both from the state cached at mount. `storage_volume_trusted()` is false only for `MISMATCH`; the dispatcher then refuses every opcode but `DEVICE_STATUS` and `UPDATE_FIRMWARE`, and `storage_secure_wipe()` refuses outright (guard inside the function, so no caller can miss it). `storage_volume_may_mint()` is additionally false for `UNMARKED`-and-empty — the exact fingerprint of a misdeclared partition: it mounts, and it looks factory-fresh. `ca_provision()` / `ca_gen_key()` return `-EPERM` → `ERR_VOLUME_INVALID` (17). Three things the design hadn't settled: (1) `UNMARKED` had to be split by whether slot 0 holds a key, or every pre-marker device (including both dev units) would have been stranded; slot 0 is the right signal rather than the session slot because nothing creates it implicitly. (2) `RESET_DEVICE` is **refused** in degraded mode, breaking the "a wipe always recovers" rule — wiping an unidentifiable volume erases something unknown and leaves the real keys intact elsewhere on the part, and a wipe that doesn't wipe what the operator thinks is worse than a refusal; `UPDATE_FIRMWARE` is the recovery path. (3) `DEVICE_STATUS` grew a volume-state byte at offset 27 (wire 27→28 B) because `ERR_VOLUME_INVALID` alone doesn't tell an operator what to do. 202,444 B (+1,232). Suites: 16 / 192 tests (volume_marker 16→21, ca_bootstrap 8→9). See the identity paragraph below for the half that completes it.

**RAM-only identity on an unverified volume (2026-07-23):** `session_slot_init()` no longer persists an identity it cannot justify, and `client_bond_add()` no longer persists a bond there (`-EROFS`, which pairing treats as "accepted for this session"). Both mint into RAM instead. The earlier framing of this as "not key loss" was too generous: a misdeclared partition is typically a **subset** of the correct one — the hardware recipe aims a build at `0x180000+0x80000` inside a real volume of `0x0+0x200000` — so every block the wrong mount allocates lands inside the live filesystem's extent and can corrupt it, CA metadata pair included. Having no identity at all is worse than a throwaway one: no Noise static key means no handshake, no wire, and on the mcuboot tier (`CONFIG_MCUBOOT_SERIAL=n`, no UF2) no recovery short of SWD. It is deliberately **not** FICR-derived — that ID is the USB iSerial, and an identity anyone who has seen the device can reproduce is a false one; unpinnable is the honest state for a device that cannot reach its own key. Checked before committing to the design: the host key store is keyed by the device's Noise static key, so a degraded device looks like a stranger and **cannot overwrite the real device's pinned entry**; tiers 2–4 refuse it, and `--trust none` + a fresh `cantil pair` is the recovery path (documented in [docs/reference/protocol-and-client.md](docs/reference/protocol-and-client.md)). That was already true before the change — the old code minted a *persistent* new identity on the wrong volume, which no pinned client accepted either — so this costs no reachability and only stops the writes. 203,724 B (+1,280), RAM 74,912 B (+1,088: a 1 KB static cert buffer). Suites: 16 / 196 tests (session_slot 24→27, client_bond 9→10). **Still writing on a degraded volume:** `storage_fw_pending_set()`, left alone deliberately — it is on the one route out.

**wolfSSL port — steps 2–4 landed (2026-07-23):** the firmware's X.509 and ASN.1 *writers* are now backend-independent; `ca.c` holds only mbedTLS **readers**. Step 2: `cantil_zeroize` ([firmware/src/crypto/zeroize.c](firmware/src/crypto/zeroize.c)) replaced 43 `mbedtls_platform_zeroize` calls, removing an mbedTLS dependency from files that otherwise had none. **wolfSSL port — step 5 landed, and the host X.509 library is now swappable (2026-07-23):** the plan said "port `trust.c` to wolfSSL"; it became a *seam* instead, because the client may want OpenSSL. [libcantil/src/x509.h](libcantil/src/x509.h) is three functions (`subject_der`, `subject_cn`, `verify_chain`), bytes in and bytes out, with `x509_mbedtls.c` (**default** — Fedora packages it, so the CLI still builds with no setup), `x509_wolfssl.c` (matches the firmware) and an `openssl` slot reserved. Chosen with `-DCANTIL_HOST_CRYPTO=`; `trust.c` now names no certificate library, and `cantil version` reports which one is compiled in. New [scripts/setup_wolfssl_host.sh](scripts/setup_wolfssl_host.sh) builds a host wolfSSL (Fedora packages none) from the same revision `west.yml` pins — with CMake, because the checkout has no `./configure` and regenerating one needs `libtool` this host lacks, and with `-DCMAKE_INSTALL_LIBDIR=lib`, because wolfSSL installs to `lib64` while the `wolfssl.pc` it generates hardcodes `libdir=.../lib`. **Two bugs, found by writing the first test this path ever had** (20 checks per backend against golden values from the *openssl CLI*, so neither backend is its own oracle): (1) **Tier 3 and Tier 4 never worked, in shipped code** — the profile allowed only `MBEDTLS_PK_ECDSA`, but mbedTLS checks `allowed_pks` against the end-entity's *public key* type too, and an EC public key is `MBEDTLS_PK_ECKEY`, so every leaf failed `BADCERT_BAD_PK` and no CA-allowlist check could ever succeed; invisible because Tier 2 compares a fingerprint and never consults the profile, and Tier 2 is what both dev units use. (2) **the wolfSSL backend trusted attacker-supplied intermediates** — wolfSSL has no untrusted-chain-material concept, so `CertManagerLoadCABuffer` makes anything loaded a *trust anchor*; the obvious translation let a peer send a self-signed cert as its "intermediate" and be accepted against any anchor, which `test_chain_wrong_anchor` caught. Replaced with incremental path building. **Specified, not incidental:** `subject_der` returns the full DER TLV — mbedTLS's `subject_raw` spans it, wolfSSL's `subjectRaw` starts after the tag and length, and a backend returning contents alone would silently break every Tier 2 subject pin. No firmware change, so no image moved. **wolfSSL port — steps 6a + 6b landed, PHASE 2 COMPLETE (2026-07-24):** mbedTLS is gone from the firmware. wolfCrypt backs all four crypto seams (`crypto.h`, `noise_crypto.h`, `ca/certgen.h`, `ca/certparse.h`); the default build links only wolfSSL and `nm` finds zero `mbedtls_*` symbols. **Step 6a:** `ca.c`'s ~71 mbedTLS *reader* refs moved behind [firmware/src/ca/certparse.h](firmware/src/ca/certparse.h) (reader mirror of `certgen.h`, bytes-in/typed-struct-out); `certparse_wolfssl.c`'s chain walker is hand-written on `wc_CheckCertSigPubKey` because a WOLFCRYPT_ONLY build has no library chain verifier, and its negative cases pin the same trust-anchor trap the host seam hit. **Step 6b:** the independent oracle moved from "mbedTLS parses wolfCrypt's output" to **OpenSSL** — [scripts/openssl_gate.sh](scripts/openssl_gate.sh) runs the `openssl` CLI over every DER artifact a generation suite dumps ([firmware/tests/common/test_artifacts.h](firmware/tests/common/test_artifacts.h)), wired into `scripts/test.sh`. `-check_ss_sig` is mandatory (OpenSSL trusts an anchor by identity and would pass a self-signed cert with a corrupted signature — confirmed by mutation); the CRL, the encoder with the least library cover, is paired with its issuer and `openssl crl -verify`'d. With the oracle in place the six `*_wolfssl` sibling suites collapsed onto their originals, the seven backend-agnostic suites switched sources, and test-side cert/CSR generation moved to [firmware/tests/common/test_pki.h](firmware/tests/common/test_pki.h) (wrappers over the firmware's own `certgen` + `crypto_keygen`). `clients/pairing.c`'s direct `mbedtls_hkdf` became `crypto_hkdf_sha256()` on the `crypto.h` seam, pinned by `crypto_kat` against RFC 5869 TC1 + a fixed pairing-PSK vector. **ACCELERATED removed** in the same phase (unselectable since upstream-Zephyr, never paired on hardware, blobs un-distributable under GPLv3 §7, and its cert writing depended on `certgen_mbedtls.c`). **Open question settled: `mbedtls` dropped from `west.yml` entirely** — OpenSSL is the oracle now, so a second crypto library in the manifest buys nothing. **Cost:** FREE was 203,752 B; wolfCrypt-only is 246,084 B (uf2) / 250,032 B (mcuboot) — footprint up, as step 1 predicted; the win is ML-KEM/ML-DSA + a single GPLv3 stack. Suites: 17 dirs, all green with the gate active. Full retrospective in [docs/roadmap/wolfssl-migration.md](docs/roadmap/wolfssl-migration.md).

**USB device stack ported to `usbd_*` — build-verified, hardware pending (2026-07-24):** `transport_usb.c` rewritten against the device_next stack; the legacy `usb_enable()` / `<zephyr/usb/usb_device.h>` path is gone — the last thing pinning the tree to v4.3.1. `prj.conf` now sets `CONFIG_USB_DEVICE_STACK_NEXT=y` + `CONFIG_USBD_CDC_ACM_CLASS=y` + `CONFIG_HWINFO=y` and drops the legacy `USB_DEVICE_VID/PID/MANUFACTURER/PRODUCT`; VID `0x1209`/PID `0x00CA` and the strings live in C now, the serial descriptor comes from HWINFO (same FICR iSerial as before, so `capture_boot_log.sh` still matches). The context is built + enabled from `transport_usb_init()` (from `main()`, past all SYS_INITs — the SET_ADDRESS race the legacy port hand-guarded can't recur); on the nRF UDC (`can_detect_vbus`) enable fires on `USBD_MSG_VBUS_READY`. **Gotcha:** the board would otherwise auto-instantiate `subsys/usb/device_next/app/cdc_acm_serial.c` — its own usbd context (Zephyr VID `0x2fe3`, first CDC only) that seizes `zephyr_udc0` at boot — so `prj.conf` sets `CONFIG_CDC_ACM_SERIAL_INITIALIZE_AT_BOOT=n`; `transport_usb.c` owns the one context and registers both CDC instances (protocol=IF0, console=IF2, order load-bearing for host `discover_usb.c`). Both tiers build (uf2 252,384 B; mcuboot app clean); `nm` confirms only `cantil_usbd` and two CDC instances. **Hardware-validated 2026-07-24 — see the milestone below.** Detail in [docs/roadmap/zephyr-upstream.md](docs/roadmap/zephyr-upstream.md).

**usbd_* port validated on hardware — two real bugs found and fixed (2026-07-24):** flashing the new wolfCrypt + `usbd_*` firmware to XIAO unit #2 surfaced two defects that only appear on-target (native_sim catches neither). **(1) RX was never armed** ([firmware/src/transport/transport_usb.c](firmware/src/transport/transport_usb.c), commit 063b8ec): the port kept the legacy `uart_poll_in()` loop, but the device_next CDC ACM class only reads the host→device (OUT) endpoint once the app enables interrupt RX — `usbd_cdc_acm_enable()` re-arms the endpoint only when `CDC_ACM_IRQ_RX_ENABLED` is set, and `cdc_acm_poll_in()` drains an `rx_fifo` nothing fills. So *every* Noise_XX handshake died with `recv timeout` (-ETIMEDOUT). Fixed with an ISR that drains the class FIFO into a ring buffer + `uart_irq_rx_enable()` in `transport_usb_init()`; TX stays on `uart_poll_out()`. **(2) fresh-boot cert-gen overflows the 12 KB main stack** ([firmware/prj.conf](firmware/prj.conf) → 24 KB, commit 1a4d23c): wolfCrypt's `WOLFSSL_SP_NO_MALLOC` keeps the P-256 SP intermediates + the ~5 KB `Cert` struct on the stack, and the 12 KB was sized for mbedTLS and never re-validated after the wolfSSL port. On a fresh/wiped boot, `session_slot_init()`'s identity mint MPU-faults mid `wc_MakeCert`/`wc_SignCert`, and because the fault kills the thread before usbd services EP0, USB never enumerates (host logs `device descriptor read, error -110` — looks bricked, is a stack overflow). Bisected by halting after each init step. **Validated with both fixes:** enumerates `1209:00ca`, dual-port order (IF0 protocol / IF2 console), boot-log console works, fresh-boot mint completes, Noise_XX handshake + `status` + an encrypted app round-trip all succeed, and `storage_secure_wipe` works. **Still owed:** `PROVISION_CA` (0x34) needs a tap-confirm to pair+unlock, and the tap button (D0/P0.02) did not register on unit #2 — firmware button path verified sound (binding present, init order/pin OK), so a likely loose wire; deferred pending a physical button check. `LOG_BACKEND` note: the USB CDC console (IF2) streams live logs, so the 2026-06-02 "logs are RTT-only" memory is stale.

**USB reconnect transport reliability — FIXED + hardware-validated (2026-07-24, commit 1d32ff1):** on the `usbd_*` firmware, a fresh CLI connection failed *perfectly alternating* — every other attempt — between `Noise_XX handshake failed` (corrupted msg2) and `CANTIL_ERR_PROTOCOL`/"Unexpected response". The earlier "stale TX frame" framing was imprecise; the true root cause is a **teardown race**: on client disconnect the device stayed blocked in `raw_recv_exact` for the full `RECV_TIMEOUT_MS` (2 s) waiting for the next command, and a client that reconnected and sent its Noise msg1 inside that window — the host waits only 700 ms before msg1 (`libcantil/src/transport_usb.c`) — had those bytes consumed *as a command frame in the dead session*, desyncing every following frame. Fix (three parts): (1) `transport.h` gains an optional `connected` vtable predicate (NULL = assume connected, so tests/loopback are unaffected); (2) `session.c`'s `raw_recv_exact` aborts with `-ENOTCONN` the instant the peer disconnects instead of blocking to the timeout, so `main()` closes the session and is back at a clean `session_open()` before the next msg1; (3) `transport_usb.c` DTR detection is now **event-driven** via `USBD_MSG_CDC_ACM_CONTROL_LINE_STATE` on the protocol port (the 100 ms `dtr_work` poll stays as a backstop), shrinking the window in which a dead session can eat a new client's bytes from ~2 s to ~1 ms. The two prior host-side mitigations (e3fd3f1, 5aab1df) remain as belt-and-suspenders. **Before/after on unit #2, same test:** a 30-reconnect `cantil status` loop went 15 pass / 15 handshake-fail → **30/30**, then **80/80** on a tighter hammer (110/110 total, zero failures). This unblocks `PROVISION_CA` end-to-end.

**`PROVISION_CA` (0x34) — mechanism hardware-validated, final mint-on-tap not captured (2026-07-25):** with transport now reliable (1d32ff1), the tap-confirm path was exercised on unit #2 and **proven at the firmware level via the IF2 console**: `cantil provision-ca` opens the session, the device enters `AWAITING_CONFIRM` (state 5, slow-yellow `LED_PATTERN_CONFIRM_PROMPT`), the gesture engine registers each tap (`tap +N`, white-flash `LED_PATTERN_TAP_ACK` per tap) and accumulates digits, compares against `SEQ_CONFIRM={3,3,3}`, and correctly **denies** on mismatch/timeout — clean session teardown each time (the reconnect fix's `peer disconnected during recv` fired on host close). The only step not captured is the mint firing on a *successful* `{3,3,3}`, blocked purely by **bare-wire input**: the D0/P0.02 test wire chatters (a single touch breaks contact for ~143 ms, past the 20 ms `debounce-ms`, so it double-registers), which repeatedly produced `{4,3}`/`{3,3}` instead of `{3,3,3}`. That last step is input-only, not firmware — the wolfCrypt mint (`wc_MakeCert`/`wc_SignCert`) is already proven on this hardware by the fresh-boot session-identity path (it's what BUG 2 overflowed) and by the ztest suites. Along the way, `libcantil` `map_proto_err()` was fixed (f7c2360) — `PROTO_ERR_BUSY` (denied/timed-out confirm) now maps to `CANTIL_ERR_TIMEOUT` instead of the misleading "unexpected response". **To finish definitively:** a tuned test image (bump `debounce-ms` to ~200 ms to absorb wire chatter and/or `SEQ_CONFIRM={1}`) or a real button, then one clean provision. The 30 s `CONFIG_CANTIL_CONFIRM_TIMEOUT_SEC` was comfortable once contact worked; a 30 s / 60 s override build exists (`build.sh -- -DCONFIG_CANTIL_CONFIRM_TIMEOUT_SEC=<n>`, not committed).

**libcantil off mbedTLS — OpenSSL is the client default now (2026-07-24):** the host X.509 seam ([libcantil/src/x509.h](libcantil/src/x509.h)) dropped its mbedTLS backend; `x509_openssl.c` is written, passes all 20 `test_x509.c` conformance checks, and is the default (`-DCANTIL_HOST_CRYPTO=openssl`), with `x509_wolfssl.c` retained as the alternate (also 20/20). mbedTLS is now gone from firmware **and** client. OpenSSL was chosen over wolfSSL-for-the-client because libcrypto is the cert library a Linux host is most likely to already have and is the same third implementation the fixtures + firmware gate are generated from; the OpenSSL model puts intermediates in an untrusted `STACK_OF(X509)` (only the caller's anchor is trusted), so the self-signed-intermediate trap the wolfSSL backend needed hand-built path building for does not arise. Profile (P-256/SHA-256) is enforced on the leaf manually since OpenSSL has no profile struct. Needs only `openssl-devel` (headers + `libcrypto.so`); the `CANTIL_CLI_STATIC` AppImage path links libcrypto **dynamically** — Fedora ships no static OpenSSL and `libcrypto.so` is a base-system library, so only libsodium is bundled statically. Detail in [docs/roadmap/wolfssl-migration.md](docs/roadmap/wolfssl-migration.md).

**ztest suites run under Bazel — 17/17 (2026-07-26):** every suite in `firmware/tests/` is now a `bazel test` target on `native_sim/native/64`, alongside the `//firmware:cantil` firmware that started linking the same day. `bazelisk test //firmware/tests/... --config=sim` builds each suite as its own Zephyr app from its existing `prj.conf` / `Kconfig` / `boards/native_sim.overlay`, via the `cantil_ztest` macro in [firmware/tests/ztest.bzl](../firmware/tests/ztest.bzl) over zephyr-bazel's `ztest()` rule; `.bazelrc` gained `--config=sim` and `--config=xiao` because no target implies its platform. Three things the port needed: `//firmware` exports its `src/**/*.c` plus three narrow header targets (Bazel `srcs` cannot cross a package with `../`, and each suite should see only the include path its CMakeLists grants it); `hdrs` must glob the suite's own `.h`/`.inc` (Bazel stages nothing a target does not declare); and **two more zephyr-bazel coverage gaps** — Zephyr registers the host-side half of the native_sim drivers with `target_sources(native_simulator INTERFACE ...)`, which the BUILD generator drops, so `entropy_native_seed` and `flash_mock_{init,cleanup}_native` were undefined for any native_sim app that mounts a filesystem (now `cc_library` targets gated on `CONFIG_FAKE_ENTROPY_NATIVE_SIM` / `CONFIG_FLASH_SIMULATOR`; the same gap remains for the other bottom-half drivers and is worth upstreaming). **Sandboxing found a real bug:** `pairing` and `pairing_passkey` passed under CMake only because native_sim's flash simulator is file-backed — `flash.bin` persists in the working directory, so they inherited a volume marker written by an earlier suite. Running the *CMake* binaries in an empty directory reproduced the 3 failures, confirming it pre-dated Bazel; fixed by having `suite_setup()` call `storage_volume_marker_write()` like the five suites that already did. **`scripts/test.sh` stays authoritative** until the OpenSSL gate ([scripts/openssl_gate.sh](../scripts/openssl_gate.sh)) is a Bazel test — under Bazel `CANTIL_TEST_ARTIFACT_DIR` is unset, so the artifact writes are no-ops and the third-implementation check does not run. Detail in [docs/roadmap/bazel-migration.md](roadmap/bazel-migration.md).

**Versioning scheme settled; bumped to 0.2.0 (2026-09-22):** `0.1.0` had been the version everywhere (`MODULE.bazel`, the three CMake `project()` calls) since a very early commit, unbumped through the wolfSSL port, the GPLv3 relicense, the Bazel migration, and the MCUboot→wolfBoot swap. Decided: unified SemVer 0.x — one version number across the repo tag, `MODULE.bazel`, and CMake `project(VERSION …)`, minor bump per milestone, patch for fixes, staying pre-1.0 until wolfBoot + BLE + non-XIAO boards land. `CANTIL_FW_IMAGE_VERSION` (a separate, strictly-monotonic firmware-image counter for anti-rollback) doesn't exist yet — it left with MCUboot on 2026-07-26 — so there is currently nothing to split it from; that decision is deferred to wolfBoot Phase 4, when the image-version Kconfig returns.
